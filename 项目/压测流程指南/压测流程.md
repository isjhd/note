# 压测流程

压力测试是通过不断向被测系统施加“压力”，测试系统在压力情况下的性能表现，考察当前软硬件环境下系统所能承受的最大负荷并帮助找出系统瓶颈所在，也就是我们可以模拟巨大的工作负荷以查看应用程序在峰值使用情况下如何执行操作。





## 测什么

### 高并发写操作

**举例**：抽奖接口属于典型的**高并发写操作**场景，压测的核心目标不只是 "能扛多少 QPS"，更关键的是验证

- **数据一致性**：高并发下会不会超卖、重复中奖
- **系统吞吐量**：极限 QPS 是多少
- **响应延迟**：P95/P99 延迟是否可接受
- **稳定性**：长时间运行会不会内存泄漏、连接耗尽

## 案例1

> 在 4C8G 服务器、100M 带宽的部署架构下，我们核心抽奖接口的稳定吞吐量是每秒 400 次，平均响应时间 300 毫秒，错误率低于 0.7%，P95为621，完全满足业务上线初期的流量需求。

- TPS ≈ 400：系统的 “处理能力上限”。1 秒钟内能成功处理完 400 次用户抽奖请求。
-  RT ≈ 300ms：系统的 “响应快慢”。用户点一次 “抽奖” 按钮，从点击发出请求，到页面返回抽奖结果，平均耗时 0.3 秒。



### 流程

#### 1. 明确压测目标和范围

- 先定清楚这次压测要测什么、达到什么标准。
- 核心目标两个：一是摸底核心抽奖接口的真实性能，测出 TPS、RT 这些关键数据，给上线容量规划做参考；二是通过高压流量暴露代码里的性能问题和隐藏 bug，做针对性优化。
- 范围就聚焦在核心的抽奖接口，这是业务流量最高、最容易出问题的链路



#### 2. 搭建压测环境和全链路监控

为了保证压测结果准确，不互相干扰，我们用了 3 台阿里云 4C8G、100M 带宽的服务器，按功能拆分部署：

- 一台专门做压测和监控：部署 JMeter 发压，搭配 Prometheus+Grafana 做指标采集和可视化
- 一台放所有中间件：MySQL、Redis、RabbitMQ、Nacos、ES 这些
- 一台跑应用服务：部署 2 个抽奖服务实例、Nginx、xxl-job 调度中心

监控覆盖了四个维度：服务器 CPU / 内存 / 磁盘、JVM 堆内存与 GC、接口 TPS/RT/ 错误率、中间件连接数与负载，保证压测中能看到全链路的指标变化。



#### 3. 数据调优

应用层：把 Tomcat 最大线程从默认 200 调到 800，调整等待队列和连接数；业务线程池和数据库连接池也按实例配置做了对应调优，MySQL 全局最大连接数调到 2000



#### 4. 设计压测场景，梯度加压

用 JMeter 写压测脚本，userId 用动态参数，模拟不同真实用户，避免单用户缓存命中过高导致结果不准。

我们做了 8 个梯度的并发测试：50、100、150、200、250、300、350、400 线程，每个线程循环请求 200 次。加压方式是平滑递增，Ramp-up 时间设为线程数的 1/10，模拟真实流量逐步上涨的场景，而不是瞬间打满。



#### 5. 压测脚本编写

1. 新建测试计划，添加线程组，设置 8 个梯度的线程数：50、100、150、200、250、300、350、400
2. 每个线程组设置循环次数 200 次，Ramp-up 时间 = 线程数 / 10
3. 添加 HTTP 请求，配置抽奖接口：
   - 请求方式：POST
   - 地址：`http://应用服务器IP/api/v1/raffle/activity/draw`
   - 请求头：`Content-Type: application/json`
   - 请求体：`{"userId":"${随机用户ID变量}","activityId": 100301}`
4. 添加察看结果树、聚合报告，用于查看压测结果



#### 6. 执行压测

1. 启动 Prometheus + Grafana，配置好应用、服务器、中间件的监控大盘
2. 命令行执行 JMeter 压测命令，后台运行并输出结果文件：`jmeter -n -t remote-50-450-200-gt-draw.jmx -l result.jtl`

3. 压测过程中实时监控 Grafana 看板，记录每个梯度下的 TPS、RT、错误率、服务器资源、JVM 状态等数据

压测过程中实时盯监控，记录每个梯度下的 TPS、RT、错误率和资源使用率。

最后输出完整的压测报告，给出最终性能结论：优化后核心抽奖接口稳定 TPS 400，平均 RT 300ms，错误率低于 0.7%，满足业务上线要求。



#### 7. Arthas 瓶颈定位

下载并启动 Arthas：`java -jar arthas-boot.jar`，选择对应 Java 进程

从入口开始逐层追踪方法耗时：

```
# 追踪Controller入口
trace com.ben.trigger.http.RaffleActivityController draw --skipJDKMethod false
# 向下追踪抽奖策略核心方法
trace com.ben.domain.strategy.service.AbstractRaffleStrategy raffleLogicChain
trace com.ben.domain.strategy.service.rule.chain.ILogicChain logic
# 定位到具体耗时方法
trace com.ben.domain.strategy.service.armory.IStrategyDispatch getRandomAwardId
```

根据耗时占比，锁定 3 个瓶颈点，对应做代码优化



#### 8. 优化后复测

修改代码重新部署后，再次执行相同的压测场景，对比优化前后的 TPS、RT、错误率数据，验证优化效果，最终输出完整压测报告。

### 遇到的问题

第一个是 xxl-job 调度中心一开始放在中间件服务器上，跨机器跨 Docker 容器，调度中心连不上应用里的执行器。后来把 xxl-job-admin 迁到应用服务器，走 Docker 内部桥接网络，配置正确的注册地址就解决了。

第二个是最初压测 TPS 一直上不去，排查发现数据库连接池默认只有 10 个，大量线程在等待数据库连接，把连接池参数调大、同步调高 MySQL 最大连接数后，性能立刻就上来了。
