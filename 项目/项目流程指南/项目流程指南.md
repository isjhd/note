# 项目流程指南

## 需求阶段

拿到一个新需求，你一般怎么做？

> 先理解业务目标，梳理业务流程，确认边界条件、异常场景；有疑问找产品 / 测试对齐，拆解技术点，评估开发工作量与风险点，输出简单接口文档或者方案，再开始编码。



如果产品需求写的模糊、逻辑有漏洞，你怎么处理？

> 不要说直接自己改逻辑。回答：主动找产品沟通，把疑问点、边界 case 列出来，对齐清楚；如果存在技术风险，同步风险和备选方案，确认后再开发，不自己脑补业务逻辑。



需求变更中途来了，你怎么处理？

> 评估改动范围、影响接口、数据库、测试工作量；同步给组长、产品，评估排期，不能直接偷偷改代码。



## 协作阶段

和前端对接接口，出现参数理解不一致，你怎么解决？

> 输出接口文档，对齐入参出参、错误码；联调出现问题优先抓日志定位，分清是前端传参问题还是后端逻辑问题。

跨服务协作，依赖别的团队接口还没开发完，你怎么办？

> 做 mock 数据；约定好接口契约；跟进对方排期；做好降级兼容逻辑。

开发任务延期了你怎么处理？

> 尽早暴露风险，不要等到截止日才说；梳理阻塞点，评估哪些可以裁剪，同步组长重新排期。



## 评审阶段

什么场景需要做方案评审？

> 涉及数据库变更、分布式事务、限流降级、大流量接口、复杂业务、重构、性能改动，需要评审。简单 CRUD 不需要。

做技术方案你会写哪些内容？

> 业务背景、需求、整体流程、接口设计、数据库变更、异常处理、风险点、限流降级、回滚方案。

你做代码评审主要看什么？

- 业务逻辑正确性，边界、异常有没有处理
- 数据库：索引、事务、锁、大查询，有没有慢 SQL 风险
- 接口：参数校验、空判断，有没有内存泄漏，资源是否关闭
- 代码可读性，重复代码，有没有硬编码
- 并发场景：线程安全，分布式场景问题

如果别人 Review 你的代码，提了你不认同的意见，你怎么做？

> 先听对方理由，一起讨论；如果对方建议合理就修改；如果有分歧，拿业务场景、性能数据说话，找组长确认，不要直接争执。

你会拒绝什么样的代码合并？

> 缺少异常处理、存在 SQL 风险、没有处理并发问题、没有单元测试、逻辑不符合需求。



## 测试阶段

开发完，你自己会做哪些自测？

> 单元测试；正常流程自测；边界值、异常 case；接口参数非法、并发场景；数据库数据正确性。交给测试之前先把明显 bug 过滤掉。

测试提了 bug，你怎么排查？

> 复现问题，看日志、入参、数据库数据；区分是业务 bug、参数问题、环境问题；修复完成回归自测再转给测试。

测试环境和生产环境表现不一致，你怎么排查？

> 配置差异、网络、中间件版本、数据不一样、环境特殊开关；对比配置、日志，还原现场。

会不会写单元测试？什么场景写单元测试？

> 核心业务逻辑、工具类、复杂计算、抽奖扣库存这类核心逻辑写单元测试；简单接口可以不用重点写。



## 发布阶段

你们项目完整上线流程是什么？

> 自测完成 → 测试环境测试通过 → 合并代码到发布分支 → 预发布验证 → 运维打包构建；灰度发布 / 分批发布；上线后观察日志、监控指标（TPS RT 错误率）；出现问题具备回滚能力。

什么是灰度发布，为什么要用？

> 先放一小部分流量到新版本，观察监控，没问题再全量上线；降低全量发布带来的线上故障风险。

上线前需要确认哪些东西？

- SQL 脚本是否正确，有无锁表风险
- 配置文件是否更新
- 有没有开关，支持降级回滚
- 监控、告警是否配置
- 回滚方案准备好

上线之后发现线上 bug，你怎么做？

> 优先止损：如果问题严重，立刻回滚版本；保留现场日志；线下复现定位根因；修复、重新测试，二次发布；事后复盘为什么漏测。

如果上线 SQL 执行，线上大表加索引，你要注意什么？

> 避免锁表，尽量低峰期执行；避免业务高峰期 DDL；评估执行时间。

什么情况下不建议上线？

> 核心功能测试未完成；存在高危 bug；没有回滚方案；大流量变更没有灰度；业务高峰期。
