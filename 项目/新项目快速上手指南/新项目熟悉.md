# 新项目熟悉

新人接手一个 Java 项目，最大的痛点依次是：

1. 这个项目整体是干嘛的？结构长什么样？
2. 核心业务是怎么跑通的？数据怎么走？
3. 代码分层怎么调用？改功能要从哪下手？
4. 数据库怎么设计的？表之间是什么关系？
5. 项目怎么跑起来？部署到哪了？





**从图形的角度**

## 一、第一优先级：必画，接手者第一眼就要看

### 1. 系统分层 / 模块架构图

**核心价值**：给项目画一张「全局地图」，1 分钟让新人看懂项目的技术分层、模块划分、技术选型，建立整体认知。

这是所有沉淀文档的开篇，没有它，新人直接扎进代码会完全迷路。

**画什么（重点）**：

- 纵向：技术分层（表现层 → 业务层 → 持久层 → 数据存储层），标注每层用的技术栈（Spring MVC、Spring Boot、MyBatis、MySQL、Redis 等）
- 横向：核心业务模块（用户模块、订单模块、支付模块、权限模块等）
- 标注模块间的调用方向和依赖关系
- **不要画**：太细的类和方法，只到模块 / 层级粒度

**沉淀技巧**：一张图控制在 10 个模块以内，复杂项目拆成「总览架构图 + 单个模块细化图」。

### 2. 核心业务泳道流程图

**核心价值**：讲清楚项目最核心的业务链路是怎么跑通的，以及每个环节由谁（哪个模块 / 系统 / 角色）负责。

纯文字讲不清业务流转，一张泳道图能直观展示跨模块、跨系统的协作逻辑，比普通活动图实用 10 倍。

**画什么（重点）**：

- 只画**2-3 条最核心的主业务链路**（比如电商的「下单 - 支付 - 发货」、OA 的「请假审批全流程」），边角功能不用画
- 用泳道划分职责：前端、后端业务服务、数据库、缓存、第三方接口
- 标注主路径 + 关键异常分支（比如支付失败怎么回滚）
- **不要画**：每个 if/else 都画进去，细节交给代码

**沉淀技巧**：给每条核心流程配 100 字以内的文字说明，讲清「这个流程解决什么问题、触发条件是什么、最终产出是什么」。

------

## 二、第二优先级：核心必画，对接手开发最有用

### 3. 数据库 ER 图（实体 - 关系图）

**核心价值**：后端项目的本质是「数据流转」，看懂了表结构和实体关系，就看懂了一半业务。

新人改功能、排查问题，第一步往往是先找表；一张清晰的 ER 图比翻几十张表结构高效得多。

**画什么（重点）**：

- 核心实体（用户、订单、商品等）、主键、核心字段
- 实体间的关联关系（1:1、1:N、M:N），标注外键关联
- **不要画**：所有字段全列出来（字段太多会淹没关键信息），只画业务核心字段

**沉淀技巧**：可以按业务领域拆分（比如用户域 ER 图、订单域 ER 图），避免一张图太臃肿；配合简单的数据流转说明（比如「下单成功后，会写入订单表、订单明细表、扣减库存表」）。

### 4. 核心接口时序图

**核心价值**：从代码视角讲清「一个请求进来，各层之间是怎么调用的」，直接对应代码结构，新人改功能、排 bug 能快速定位到对应层级和类。

流程图讲「做什么」，时序图讲「谁按什么顺序做」，是衔接业务设计和代码实现的关键。

**画什么（重点）**：

- 只画**最核心、最复杂的 3-5 个接口**（比如登录、下单、支付回调）
- 按分层画：Controller → Service → DAO → 数据库 / 缓存 / 第三方服务
- 标注关键的入参、出参和核心逻辑节点
- **不要画**：所有接口都画，简单的 CRUD 接口完全没必要

**沉淀技巧**：用 PlantUML/Mermaid 文本化绘制，和接口代码放在对应模块的 docs 目录下，改代码时顺手更新，不容易过期。

------

## 三、第三优先级：可选加分项，用于沉淀设计思路

### 5. 核心领域类图

**核心价值**：沉淀代码的设计思路，尤其是用到设计模式、领域模型复杂的模块。

注意：**绝对不要画全量类图**—— 不仅维护成本极高，而且密密麻麻没人看。

**画什么（重点）**：

- 核心业务领域的类关系（比如订单领域的 Order、OrderItem、PayRecord 的关联）
- 用到设计模式的类结构（比如策略模式的接口 + 多个实现类、工厂模式的类层次）
- 标注类的核心方法和关键属性
- **不要画**：get/set、工具类、简单 POJO 全部省略

**沉淀技巧**：只给「设计复杂、有设计意图」的模块画，配文字说明「为什么这么设计、解决了什么问题」，价值会非常高。

### 6. 部署拓扑图

**核心价值**：解决「项目怎么跑起来、部署到哪了」的问题，让新人快速搭建环境、定位线上问题。

单体项目可以简化，分布式 / 微服务项目建议补充。

**画什么（重点）**：

- 服务器节点、数据库、缓存、消息队列的部署位置
- 网络端口、调用方向、环境区分（测试 / 生产）
- **不要画**：太细的服务器配置参数

------

## 四、高效沉淀的核心原则（非常重要）

很多项目的图最后都会变成「一次性摆设」，和代码脱节、没人维护。想让图真正有沉淀价值，记住这几条：

1. **一图一主题，拒绝大而全**

   一张图只讲清楚一件事，不要把架构、流程、类关系全塞在一张图里。

2. **用文本化绘图工具，纳入版本管理**

   优先用 **PlantUML 或 Mermaid**，把源文件放在项目的 `/docs/diagrams` 目录下，和代码一起提交 Git。

   图片格式的图无法 diff、无法同步更新，很快就会和代码脱节，完全失去沉淀意义。

3. **核心优先，20% 的图覆盖 80% 的认知需求**

   不要追求画全所有 UML 图。一个 Java 项目，沉淀好「1 张架构图 + 2-3 张核心泳道流程图 + 1 张 ER 图 + 2 张核心时序图」，就足够让新人快速上手。

4. **图 + 简短说明，比纯图有用**

   每张图配 50-100 字的说明：这张图讲了什么、适用场景、关键注意点。后人不用猜图里的细节。

5. **README 里加索引**

   在项目根目录的 README 中，给出所有文档和图的入口链接，新人一进项目就能按顺序查阅。

------

### 新人接手的标准读图路径（验证这套图的合理性）

架构图（建立全局认知）→ 核心业务流程图（懂业务怎么跑）→ ER 图（懂数据怎么存）→ 核心时序图（懂代码怎么调用）→ 类图（懂设计细节）

完全符合从宏观到微观的认知规律，能最大程度降低接手成本。
